# 보스톤늘푸른교회 — The Evergreen Church of Boston

브루클라인 한인 교회의 정적 웹사이트. Next.js 16(App Router), React 19, Tailwind CSS v4로
만들었고 모든 라우트를 빌드 시점에 미리 렌더링한다.

> **아직 교회 검수 전이다.** 교단 표기와 연락처 등 확인이 남은 항목이 있다.
> 확인 대기 목록은 저장소 밖 작업 메모로 관리한다.

## 실행

```bash
npm install
npm run dev      # http://localhost:3000
npm run build            # 모든 라우트를 out/ 으로 정적 생성
npm run lint
npm run refresh:youtube  # 유튜브 피드를 다시 읽어 content/cache/ 를 갱신
npm run refresh:gallery  # 드라이브 사진첩을 갱신 (GALLERY_URL 환경변수 필요)
```

**빌드는 네트워크를 쓰지 않는다.** 외부 소스는 각자의 갱신 워크플로가 미리 읽어
`content/cache/`에 커밋해 두고, 빌드는 그 파일만 읽는다. 이유는 아래
'외부 소스 갱신' 절에 있다.

## 구조

```
app/
  (site)/[lang]/    ko와 en 두 트리가 빌드 시점에 모두 생성된다
    layout.tsx      <html lang>, 폰트, 헤더/푸터
    page.tsx        홈. 예배 시간과 오시는 길을 최상단에 둔다
    about/ pastor/ worship/ sermons/ community/ visit/
    news/ gallery/  드라이브 폴더에서 생성된다
  (entry)/          / 하나. 언어를 감지해 /ko 또는 /en 으로 보낸다
  sitemap.ts robots.ts
components/         SiteHeader, SiteFooter, LocaleSwitcher, SermonCard,
                    SermonPlayer, PageHeader, Prose, SectionHeading,
                    EvergreenMark
content/            모든 문구와 데이터. 컴포넌트 안에 콘텐츠를 두지 않는다
  cache/            외부 소스를 읽어 커밋해 둔 것. 손으로 고치지 않는다
lib/                i18n.ts, ui.ts, youtube.ts, gallery.ts, content.ts,
                    nav.ts, asset.ts, format.ts, site-url.ts
scripts/            외부 소스를 읽어 content/cache/ 에 쓰는 갱신 스크립트
public/images/      임시 이미지. 출처와 라이선스는 아래 '이미지' 절 참고
  gallery/          드라이브에서 받아 커밋한 사진. 손으로 넣지 않는다
```

## 콘텐츠 모델

`content/`가 유일한 원본이다. 교회 이름·주소·예배 시간을 코드에 하드코딩하지 않는다.
두 번째 고객이 생겼을 때 이 구조를 그대로 복사해 `content/`만 갈아끼우기 위함이다.

**확인되지 않은 내용은 문구로 채우지 않고 비워 둔다.** "추후 안내 예정" 같은 자리표시 문장은
쓰지 않는다. 값이 없으면 해당 항목 자체가 렌더링되지 않는다.
`content/visit.json`의 `transit`가 빈 배열인 것이 그 예다.

| 파일 | 담는 것 |
| --- | --- |
| `site.json` | 교회명, 미션, 교단, 주소, 연락처, SNS 링크, 유튜브 채널 ID |

`contact`에는 번호가 둘 있다. `phone`은 화면에 보이는 표기이고,
`phoneDial`은 `tel:` 링크에 쓰는 E.164 형식이다. 보스톤에는 해외에서 오는 사람이
많아 국가번호가 없으면 그쪽에서 연결되지 않는다.
| `worship.json` | 예배와 기도회 시간, 오픈카톡 참여코드 |
| `visit.json` | 교통편, 주차, 도착 후 안내 |
| `staff.json` | 교역자 — 이름, 직함, 사역의 마음, 비전, 약력 |
| `pages/about.md` | 서술형 문구 (마크다운 + front matter) |

`staff.json`의 내용은 담임목사가 직접 쓴 소개 문서(2026-09)에서 옮긴 것이다.
한국어는 원문 표현을 그대로 두었고, 영어는 내가 옮긴 것이므로 확인이 필요하다.
연도가 적혀 있지 않은 항목은 `year`를 빈 문자열로 두었고, 그 행은 연도 없이 표시된다.
`photo`와 `photoAlt`는 **함께** 채우거나 함께 비워 둔다. 한쪽만 있으면 빌드가 멈춘다.
사람 사진에 대체 텍스트가 빠진 채로 배포되는 일을 막기 위함이다.

**형식은 의도적으로 CMS 호환이다.** 컬렉션형 문구는 front matter가 있는 마크다운,
단일 값은 JSON으로 둔다. 나중에 교역자가 직접 글을 올려야 하면
Sveltia CMS나 Pages CMS를 `content/`에 연결하기만 하면 되고, 페이지 코드는 그대로 둔다.
지금 CMS를 넣지 않은 이유는 콘텐츠 스키마가 아직 확정되지 않았고,
교역자가 직접 관리할지도 정해지지 않았기 때문이다.

라우팅은 예외다. `lib/nav.ts`의 각 항목은 실제 디렉토리가 있어야 동작하므로,
CMS 편집자가 경로를 바꿔 링크가 깨지는 일이 없도록 코드에 둔다.

## 색

팔레트는 교회 로고에서 끌어왔되, 로고 색을 그대로 쓰지는 않았다.

로고에는 세 가지 색이 있다. 잎의 초록(132°, 채도 71%), 호의 하늘색(192°),
십자가와 성경의 테라코타(20°). 이 중 초록과 하늘색을 UI에 그대로 옮기면
본문 명암비가 AA에 못 미치고(각 3.97:1, 3.54:1), 초록+시안+갈색 배색이 되어
디자인이 낡아 보인다. **하늘색은 로고 안에만 둔다.**

- 초록은 로고의 색상각 쪽으로 옮기되 채도는 낮게, 명도는 깊게 유지한다.
  낮은 채도에서는 색상을 13° 옮겨도 눈에 거의 띄지 않으므로, 이 조정 자체는
  거의 시각적 효과가 없다. 로고와 어긋나지 않게 하는 정도의 의미다.
- 유일하게 눈에 보이는 선택은 액센트다. 일반적인 금색 대신
  **로고 십자가의 테라코타**를 쓴다. 페이지에서 유일한 따뜻한 색이
  로고의 무언가를 가리키게 된다.

두 스킴의 모든 텍스트 조합이 WCAG AA를 넘는다.

## 한국어 / 영어

`/ko`와 `/en` 두 정적 트리를 빌드 시점에 모두 생성한다. 검색엔진은 양쪽을 각각 색인하고,
각 페이지는 자기 자신을 `canonical`로, 같은 페이지의 다른 언어를 `hreflang`으로 가리킨다.

**언어 감지는 브라우저에서 한다.** 정적 export에는 서버가 없어서 `Accept-Language`를
협상할 수 없고, `output: export`에서는 middleware도 동작하지 않는다. 그래서 `/`는
`app/(entry)/page.tsx`가 렌더링하는 얇은 전달 페이지다. 이 페이지는:

1. `localStorage`에 저장된 선택을 먼저 본다 (헤더의 언어 전환 버튼이 기록한다)
2. 없으면 `navigator.languages`를 본다
3. 어느 쪽도 아니면 한국어로 보낸다. 교회가 예배드리는 언어이기 때문이다

리다이렉트 스크립트는 `useEffect`가 아니라 인라인으로 넣는다. 문서를 파싱하는 동안,
React가 hydrate하기 전에 실행되어야 방문자가 전환을 눈치채지 못한다.

JavaScript가 꺼져 있으면 두 언어 링크가 보인다.

### 루트 레이아웃이 둘인 이유

`app/`에는 루트 레이아웃이 두 개 있고, 라우트 그룹으로 나뉘어 있다.

| 그룹 | 담당 | 이유 |
|---|---|---|
| `app/(site)/[lang]/layout.tsx` | 언어 트리 전체 | `<html lang>`을 언어별로 설정해야 한다 |
| `app/(entry)/layout.tsx` | `/` 하나 | 전달 페이지는 헤더·푸터·폰트가 필요 없다 |

공용 루트 레이아웃 하나로는 `<html lang>`을 언어마다 다르게 줄 수 없다.
라우트 그룹은 URL에 나타나지 않으므로 경로는 `/ko`, `/en`, `/` 그대로다.

전달 페이지를 `public/index.html`로 두지 않는 이유는 두 가지다.
`public/` 파일은 **dev 서버의 `/`에서 서빙되지 않아** `npm run dev`가 404가 나고,
Next가 `basePath`를 적용해주지 않아 링크를 상대 경로로 손수 써야 한다.
실제 페이지로 두면 둘 다 자동으로 해결된다.

### `[lang]`은 아무 세그먼트나 잡는다

`app/(site)/[lang]/layout.tsx`에 `dynamicParams = false`가 있다.
없으면 `/visit` 같은 옛 링크가 `lang="visit"`으로 해석되어,
404가 아니라 빌드 실패나 500으로 이어진다.

### 어디에 무엇을 넣는가

| | 무엇 | 어디 |
|---|---|---|
| 교회가 관리 | 예배 시간, 주소, 교회 소개 문구 | `content/` — 값 자체가 `{ "ko": …, "en": … }` |
| 개발자가 관리 | 버튼·메뉴·섹션 제목 | `lib/ui.ts` |

교회 콘텐츠는 한 파일 안에 두 언어를 나란히 둔다. 주소나 시각처럼 언어와 무관한 값은
하나만 두어, 한쪽만 고쳐서 어긋나는 일이 없게 한다.

**설교 제목은 영어 페이지에서도 한국어로 나온다.** 유튜브 업로드 제목이 원본이고,
번역할 대상이 없다.

## 외부 소스 갱신

사이트에는 교회가 다른 곳에서 관리하는 자료가 들어온다. 유튜브 설교 영상과
구글 드라이브 사진첩 둘이다.

**이 소스들은 빌드에서 읽지 않는다.** 각 소스마다 갱신 워크플로가 따로 있고,
그 워크플로가 소스를 읽어 `content/cache/`에 커밋한다. 커밋이 배포를 부른다.
빌드는 커밋된 파일만 읽는다.

```
refresh-youtube.yml  ──▶  content/cache/videos.json   ──┐
                                                         ├──▶  deploy.yml
refresh-gallery.yml  ──▶  content/cache/gallery.json  ──┘
                          public/images/gallery/
```

**소스를 서로 떼어놓기 위한 구조다.** 유튜브 피드가 죽어도 그 갱신 작업 하나만
실패한다. 사이트는 마지막으로 받아둔 설교 목록으로 계속 배포되고, 같은 시간에
올라온 사진은 정상적으로 반영된다. 반대도 마찬가지다. 한 소스의 장애가 다른
소스의 배포를 막지 않는다.

빌드가 네트워크를 쓰지 않게 된 것은 그 부수 효과다. 인터넷 없이 빌드되고,
같은 커밋은 언제 빌드해도 같은 사이트가 된다.

**갱신 워크플로는 `deploy.yml`을 `workflow_call`로 직접 부른다.** 커밋만 하고
`on: push`가 받아주기를 기다리지 않는다. GitHub은 워크플로가 무한히 서로를
부르는 것을 막으려고 `GITHUB_TOKEN`으로 만들어진 push 이벤트를 워크플로 트리거로
쓰지 않기 때문이다. 갱신 작업이 커밋만 하고 배포는 영영 일어나지 않는,
아무 에러도 나지 않는 실패가 된다. (`workflow_dispatch`와 `repository_dispatch`는
이 규칙의 예외다.)

### 설교 영상

설교 목록은 채널의 Atom 피드에서 읽는다.

```
https://www.youtube.com/feeds/videos.xml?channel_id=UC9lLWrlCsGxivAgiSZwb0ag
```

API 키도 할당량도 필요 없다. 넘겨줄 비밀값이 생기지 않는다는 뜻이기도 하다.

- `.github/workflows/refresh-youtube.yml`이 **4시간마다 :37분에** 피드를 읽고,
  목록이 달라졌을 때만 커밋한다. 새 설교가 없으면 아무것도 빌드되지 않는다.
- 즉시 반영하려면 Actions 탭에서 **Run workflow**를 누르거나
  `gh workflow run refresh-youtube.yml` 을 실행한다.
- 피드는 **최근 15개**만 준다. 전체 아카이브는 유튜브 채널에 그대로 둔다.
- 제목에서 날짜·제목·설교자를 뽑아내지만, 제목은 사람이 손으로 쓰므로
  **모든 필드가 선택적이다.** 형식이 다른 영상은 원본 제목 그대로 보여준다.
- 제목에 `주일예배 말씀`이 있으면 설교, 없으면 '교회 영상'으로 분류한다.
- 피드 요청이 실패하면 **갱신 작업이 중단된다.** 커밋이 없으므로 배포도 없고,
  직전에 받아둔 목록이 그대로 남는다. 실패는 Actions에 남아 눈에 보인다.

주기의 근거는 실제 업로드 기록이다. 주일예배는 오후 2시(ET)지만 영상은 정해진
시각에 올라오지 않는다. 피드의 설교 14개를 보면 업로드가 예배 후 **5.6시간에서
34시간 사이**에 이루어졌고, 시각은 일요일 23시 UTC부터 화요일 04시 UTC까지
흩어져 있다.

**분(minute)이 시(hour)보다 중요하다.** GitHub은 부하가 높을 때 예약 실행을
미루고, 문서가 지목하는 혼잡 시각이 *매시 정각*이다. 이전 설정인 `0 6,18`은
연속 9회 실행에서 **2시간 39분에서 6시간 59분까지** 밀려서 돌았다 —
'12시간 안에 반영'이 실제로는 15시간에 가까웠다는 뜻이다. `:37`분으로 옮기고
4시간 간격으로 돌리면, 밀리더라도 반나절이 아니라 몇 시간 손해에 그친다.

### 소식과 사진첩

둘 다 교회가 관리하는 **구글 드라이브 폴더 하나**에서 온다. 폴더는 2단이다.

```
교회 홈페이지 갤러리/
├ News_소식/                            → /news/
│  └ Korean School_한국학교/               한 페이지에 공지 전부
│       poster.jpg
└ Gallery_사진첩/                        → /gallery/
   └ Christmas_성탄절/                    → /gallery/christmas/
        *.jpg
```

**섹션이 둘인 이유는 읽는 사람에게 다른 것이기 때문이다.** 다음 학기를 알리는
포스터와 지난 성탄절 사진은 둘 다 '폴더 안의 이미지'지만, 하나는 지금 알려주는
것이고 하나는 남겨두는 것이다.

**폴더 이름이 곧 항목 정보 전체다.** 섹션 이름까지 같은 규칙을 쓴다.

```
Korean School_한국학교
└ 영문 이름           └ 한국어 이름
  └ 주소가 되는 쪽
```

**저장소에 목록이 없다.** 드라이브에 `Christmas_성탄절` 폴더를 만들면 다음 갱신에
그게 새 항목이 된다. 개발자가 손댈 것이 없다는 것이 이 구조의 전부다.
이름이 이 형식이 아니거나 최상위에 모르는 폴더가 생기면 갱신 작업이 **중단된다** —
조용히 건너뛰면 폴더를 만든 사람은 사이트에 안 나타나는 이유를 알 길이 없다.
대신 잘못된 폴더 하나가 나머지 갱신까지 막는다는 대가가 있다.

**이름이 `_`로 시작하는 폴더는 어느 위치에서든 건너뛴다.** 사이트에서 내리는 것과
지우는 것은 다르다. 지난 학기 시간표를 `_Korean School_한국학교`로 바꾸거나
`_Old` 폴더로 옮기면 사진은 드라이브에 그대로 둔 채 홈페이지에서만 사라진다.
'모르는 폴더는 무시'가 아니라 **표시한 것만 숨기는** 이유는, 모르는 폴더가
보관함보다 오타(`Galery_사진첩`)일 때가 훨씬 많아서다. 조용히 무시하면 사진이
이유 없이 사라진다. 숨긴 폴더는 Apps Script가 들어가지도 않으므로, 보관함이
아무리 커져도 목록 요청이 느려지지 않는다.

**소식에는 항목별 페이지가 없다.** 공지는 포스터 한 장이라 클릭해 들어갈 내용이
없고, 더 중요하게는 정적 export가 동적 라우트마다 최소 한 경로를 요구해서
공지를 다 지우면 빌드가 깨진다. 사진첩은 앨범이 쌓이면 하위 페이지가 필요하므로
남기되, 비었을 때를 위해 `_none` 경로 하나를 만들어 404로 렌더한다.
어디서도 링크하지 않고 sitemap에도 넣지 않는다.

날짜는 드라이브의 수정 시각을 **보스턴 시간대로** 환산해 저장한다. UTC 그대로
쓰면 일요일 저녁에 올린 공지가 월요일로 표시된다.

읽는 곳이 둘이고 **둘 다 자격증명이 필요 없다.**

| | 무엇을 | 어떻게 |
| --- | --- | --- |
| 목록 | 어떤 앨범에 어떤 파일이 있는지 | 교회 드라이브의 Apps Script 웹앱 (`scripts/apps-script/`) |
| 이미지 | 실제 바이트 | 구글 CDN — `drive.google.com/thumbnail?id=…&sz=w600` |

Apps Script는 소유자 권한으로 실행되도록 배포되어 있어서 API 키 없이 폴더 구조를
읽는다. 사진 바이트를 **거기로 실어 나르지 않는 이유**는 실측이다. base64로 보내면
1.4MB 사진 한 장에 88초가 걸렸고 세 번 중 한 번은 타임아웃이었다. 같은 사진을
CDN은 이미 리사이즈된 채로 0.5초에 준다. Apps Script는 메가바이트를 옮길 곳이 아니다.

- 사진은 **평생 한 번만** 내려받는다. 600px과 1600px 두 벌이 저장소에 커밋되므로
  빌드에 네트워크가 필요 없고, 드라이브 폴더가 사라져도 교회에 아카이브가 남는다.
- 파일명은 드라이브 **파일 ID**로 저장한다. 드라이브에서 사진 이름을 바꿔도
  커밋된 파일이 고아가 되지 않는다.
- 드라이브에서 지운 사진은 다음 갱신에 저장소에서도 지워진다.
- 대체 텍스트는 **파일 이름**에서 만든다. 사진을 올리는 사람이 설명을 쓸 리 없고
  없는 설명을 지어내는 것보다 낫다. 파일 이름을 잘 지으면 그대로 좋아진다.
- 받은 이미지에 **Exif 세그먼트가 있으면 작업을 중단한다.** 구글이 리사이즈하면서
  메타데이터를 떼는 것으로 보이지만 확인된 사실이 아니고, 교인 사진은 촬영 위치가
  박힌 폰 사진이다. 가정하지 않고 검사한다.

`GALLERY_URL`은 Apps Script 웹앱의 `/exec` 주소이고 **Actions 시크릿**에 둔다.
자격증명은 아니지만 저장소가 공개라 소스에 남기지 않는다.

### 예약 워크플로가 꺼지지 않게 하기

GitHub은 공개 저장소의 예약 워크플로를 *"no repository activity has occurred in
60 days"* 이면 자동으로 끈다. 이 시계를 되돌리는 것은 **새 커밋뿐**이다.
태그나 이슈는 세지 않는다.

평소에는 문제가 없다. 설교가 매주 올라오고 그때마다 갱신 워크플로가 커밋하므로
시계가 20일 이상 흘러갈 일이 없다. 사진이 올라올 때도 마찬가지다.

문제는 **교회가 두 달 내내 아무것도 올리지 않는 경우**다. 사이트가 죽지는
않는다 — 정적 파일이라 그대로 서비스된다. 대신 앞으로의 자동 갱신이 멈추고,
경고는 메일 한 통뿐이다. 아무 에러도 나지 않는 종류의 고장이다.

그래서 `.github/workflows/keepalive.yml`이 **매달 1일과 15일**에 `.github/keepalive`
에 날짜를 적어 커밋한다. 외부 소스를 읽지 않으므로 이 워크플로를 실패시킬 수 있는
것이 없고, 두 번 연속 건너뛰어야 60일에 닿는다.

이 워크플로는 배포하지 않는다. 저 파일은 사이트 콘텐츠가 아니고, `GITHUB_TOKEN`
으로 만든 커밋은 `on: push`를 트리거하지 않기 때문에 헛빌드도 생기지 않는다.

> **확인되지 않은 부분:** GitHub 문서는 activity를 정의하지 않는다. 봇 커밋이
> 시계를 되돌린다는 것은 '봇 커밋도 커밋'이라는 추론이지 문서로 확인된 사실이
> 아니다. keepalive가 도는데도 비활성화 경고 메일이 오면 이 가정이 틀린 것이니,
> 그때는 사람이 커밋하는 방식으로 바꿔야 한다.

## 배포

사이트 주소는 **https://evergreenboston.org** 이다. `www`와 옛 주소
`studio-hylbert.github.io/evergreenboston`은 모두 이곳으로 301 된다.

도메인은 Cloudflare에 등록되어 있고 DNS도 Cloudflare가 맡는다. GitHub Pages를
가리키는 레코드는 apex의 A 4개와 AAAA 4개, 그리고 `www` CNAME이다.
**전부 프록시를 끈 상태(회색 구름)여야 한다.** 프록시를 켜면 GitHub이
인증서를 발급하지 못한다.

커스텀 도메인 자체는 저장소가 아니라 GitHub의 Pages 설정에 저장된다.
`actions/configure-pages`가 그 설정에서 주소와 하위 경로를 읽어오므로,
도메인을 바꿔도 코드는 손대지 않는다.


`main`에 푸시하면 `.github/workflows/deploy.yml`이 lint → build → 배포까지 수행한다.
손으로 실행할 것은 없다.

저장소에 적어두지 않고 환경에서 받는 값이 둘 있다.

| 변수 | 용도 |
| --- | --- |
| `NEXT_PUBLIC_BASE_PATH` | 사이트가 서비스되는 하위 경로. **커스텀 도메인에서는 빈 값**이고, `<org>.github.io/<repo>`로 서비스될 때만 `/<repo>`가 된다. 맞지 않으면 모든 에셋이 404가 난다 |
| `NEXT_PUBLIC_SITE_URL` | `sitemap.xml`, canonical, hreflang, Open Graph의 정식 주소 |

둘 다 `actions/configure-pages`가 채우므로 저장소에 중복해 적지 않는다.
나중에 교회 도메인으로 옮길 때도 저장소 Pages 설정만 바꾸면 되고 코드는 그대로다.

배포된 빌드를 로컬에서 재현하려면:

```bash
NEXT_PUBLIC_SITE_URL=https://evergreenboston.org npm run build
npx serve out
```

`npm run dev`는 두 변수 없이 `/`에서 서비스한다.

정적 export가 기대는 두 가지:

- `public/.nojekyll` — GitHub Pages가 출력물을 Jekyll로 처리하지 않게 한다.
  없으면 밑줄로 시작하는 `_next` 디렉토리가 통째로 사라진다.
- `trailingSlash: true` — `worship.html`이 아니라 `worship/index.html`을 만들어,
  라우팅이 확장자 폴백에 의존하지 않게 한다.

## 이미지

정적 export에는 이미지 최적화기가 없다(`images.unoptimized`). 따라서 이미지는
**서비스되는 크기로 미리 만들어** 저장한다. 히어로와 건물 사진은 `next/image`가 아니라
`<picture>`로 작성했다. 뷰포트마다 정확히 한 파일만 내려받게 하기 위함이다.

유튜브 썸네일은 저장소에 복사하지 않고 `i.ytimg.com`에서 바로 가져온다.
영상이 교체되어도 썸네일이 낡지 않는다.

히어로와 건물 사진은 아직 임시다. 교회에서 실물 사진을 받으면 교체한다.

| 파일 | 내용 | 출처 | 라이선스 |
|---|---|---|---|
| `public/images/logo.png`<br>`app/icon.png`<br>`app/apple-icon.png` | 교회 로고. 십자가를 줄기로 삼은 나무가 펼친 성경에 뿌리내린 형태 | 교회 유튜브 채널 아바타에서 추출 | 교회 소유 |
| `hero-forest*.jpg` | 안개 낀 침엽수림. 홈 히어로 | [Wikimedia Commons](https://commons.wikimedia.org/wiki/File:Fog_descending_on_a_pine_forest_(Unsplash).jpg) | **CC0** — 의무 없음 |
| `church-exterior*.jpg` | 1773 Beacon St 건물 외관 | [Wikimedia Commons](https://commons.wikimedia.org/wiki/File:All_Saints_Parish_Church_1773_Beacon_Street_Brookline_Massachusetts.jpg), 촬영 EgorovaSvetlana | **CC BY-SA 4.0** |
| `church-tower.jpg` | 같은 건물, 세로 구도 | [Wikimedia Commons](https://commons.wikimedia.org/wiki/File:All_Saints_Parish_Church_Beacon_Street_Brookline_Massachusetts.jpg), 촬영 EgorovaSvetlana | **CC BY-SA 4.0** |
| `worship-service*.jpg` | 2층 Music Room에서 드리는 주일예배. `/worship` | 교회의 기존 Wix 사이트 '소식' 페이지 (원본 2048×1152) | 교회 소유 |

`church-*.jpg`는 CC BY-SA라 **출처 표기와 동일조건변경허락 의무**가 따른다.
`/visit` 페이지에 촬영자와 라이선스를 링크로 표기하고 있고, 저장소의 파일은 원본을
리사이즈한 2차적 저작물이므로 그 자체도 CC BY-SA 4.0으로 배포된다.
사이트의 나머지 코드에는 영향이 없다. 교회 사진으로 교체하면 이 의무는 사라진다.

`worship-service*.jpg`는 교회 사진이라 라이선스 의무가 없다. 다만 **교인 약 40명이
찍혀 있다.** 대부분 뒤에서 잡아 얼굴이 크게 나오지 않지만, 교회의 기존 사이트에
올라가 있던 사진을 검색에 색인되는 새 사이트로 옮기는 것은 노출 범위가 달라지는
일이다. 게재 동의는 교회에 확인할 항목으로 남겨 두었다.

이미지는 모두 픽셀 데이터만 남기고 재인코딩했다. 촬영 기기·시각·저작권 문자열 같은
EXIF는 남아 있지 않다 (GPS는 원본에도 없었다).

### 담임목사 사진

**아직 없다.** `content/staff.json`의 `photo`·`photoAlt`가 비어 있고, 값이 채워지면
그때 표시된다.

목사님이 보내신 소개 문서에 사진이 하나 있으나 사모님과 네 자녀가 함께 있는
가족 사진이다. 저장소가 public이라 한번 올린 것은 되돌리기 어렵고 미성년 자녀의
얼굴은 본인이 동의할 수 없는 것이라, 이 사진은 쓰지 않는다.
목사님만 나오도록 잘라 보았으나 밤에 찍은 셀카라 260px까지만 확보되고
화질도 좋지 않아 그것도 뺐다. **인물 사진을 따로 받을 것.**

### 로고

교회 유튜브 채널 아바타에서 가져와 흰 배경을 투명 처리했다. 외곽선 잎의 속이
비치므로 밝은 배경과 어두운 배경 모두에서 쓸 수 있다.

원본은 JPEG이고 업스케일된 것이라 헤더 크기(32px)에서 동심원 호가 다소 뭉갠다.
**교회에서 원본 벡터(AI/SVG/PDF)를 받으면 교체할 것.** 그러면 favicon과
홈화면 아이콘 화질도 같이 올라간다.
